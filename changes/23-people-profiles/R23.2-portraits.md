## Spec

**Problem:** Five new portraits arrived as iPhone HEIC (Sasho, Thomas, Natalia, Kanika, Jordan).
Photo files are named by first name under `public/eboard/`, which stops fitting once project
executives have photos and will collide on a repeated first name. The optimizer's `PORTRAITS`
list still names three departed members. Existing photos are 3:2 landscape, hand-framed per
person with an `objectPosition` and a blanket `scale-125`. The new ones are 3:4 portrait, so the
same zoom would crop their heads.

**Approach:**

1. **HEIC conversion stays outside the repo.** sharp's prebuilt libvips reads AVIF but not HEVC
   HEIC, and Ubuntu's libheif 1.17 rejects these files (iOS 18 `tmap` gain-map brand). They were
   converted with `pillow-heif` 1.8.0 (libheif 1.23.4) in a scratch virtualenv: JPEG quality 95,
   4:4:4 chroma, Display P3 ICC profile kept, EXIF dropped (rotation is already applied to the
   pixels; EXIF can carry GPS). Document this in the script header so the next batch from the
   Drive follows the same path. No Python dependency is added to the project.
2. **Files keyed by person id.** Sources become `scripts/source-images/<person-id>.jpg`, outputs
   `public/people/<person-id>.webp`. Existing photos are renamed with `git mv` (Julian, Praneeth,
   Nila, Aayushi). Kanika's old source and the three departed members' sources move to
   `scripts/source-images/retired/` (kept in git, not regenerated). `PORTRAITS` lists ids.
3. **Color.** sharp converts the embedded P3 profile to sRGB on output. Verify it rather than
   assume it: compare a skin-tone sample from the WebP with a reference that Pillow `ImageCms`
   converts from P3 to sRGB. A naive conversion that drops the profile would differ visibly
   (more desaturated).
4. **Photo metadata in the model.** Each `photo` records its real output `width`/`height` (the
   script prints them) instead of the current hard-coded `964x640` on every `<img>`.
5. **Consistent framing.** Replace the blanket `scale-125` plus ad-hoc `styleAdjustments` with a
   per-photo `position` (and optional `scale`) in `PersonPhoto`, tuned so the faces sit at a
   similar size and height across the grid, old landscape and new portrait photos mixed. Tune by
   screenshot at both breakpoints.

## Notes / log
- 2026-10-05 - **Deviation: crop in the optimizer instead of framing in CSS** (supersedes items 4
  and 5). Each portrait is cropped to a uniform 720x900 (4:5) head-and-shoulders frame from a
  per-person face box (center x, head top, chin; fractions of the source) in `PORTRAITS`, which
  puts the head top at 14% and the chin at 50% of every output. All cards then share one CSS
  rule (`object-cover`, no `scale-125`, no per-person `objectPosition`), and `photo` is a plain
  URL with a shared `PORTRAIT_SIZE`. This is sharper (the old CSS showed about 410x512 source
  px per card) and keeps future avatars (R23.3) consistent for free. The June 2026 auto-crop
  failure came from sharp's `attention` strategy guessing the subject; explicit boxes do not.
  Face boxes were tuned in two passes against a guide-line contact sheet (the script writes one
  to the OS temp dir). Julian's and Praneeth's 2025 landscape sources have too little headroom,
  so their heads sit at about 10% instead of 14%. Fixing that would push the face to half the frame.
- 2026-10-05 - Gate: `pnpm optimize:images` exit 0, nine WebPs of 32-127 KB (812 KB total). The
  regenerated icons and OG card are byte-identical (git shows no change). Color: with a
  Pillow-shrunk P3 sample fed to both, sharp's sRGB conversion matches LittleCMS within 0.01/255.
  On warm pixels (faces, logo) the q78 WebP path's signed bias is about -1 to -2 red against the
  reference, versus about -6 to -7 for a profile-ignoring conversion, so the pipeline is
  color-managed. (A first attempt that compared whole frames resized by different tools could not
  tell correct from naive conversion, about 3/255 either way, and was discarded.) Lint 0
  findings, build 0. Production preview at 1440x900 and 390x844: 9 `/people/` images, no
  `/eboard/` requests, no broken images, failed requests, or console errors, no overflow.
  Viewport screenshots committed (`screenshots/eboard-*.png`).
- 2026-10-05 - CLS investigation. The first runs showed intermittent CLS of about 0.1 on the
  branch. Attribution traced it to the footer leaving the viewport while the test was already
  scrolling the route's loading screen (network idle fired before React rendered the lazy

  size give identical numbers on main and the branch: 0.0005 desktop, 0.0148 mobile, no footer
